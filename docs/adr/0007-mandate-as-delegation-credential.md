# ADR-0007: Mandate as an AgentDelegationCredential

- **Status**: Accepted (2026-10-02, contract V2). Links: D11, R1, I7, T-V1, [02 §11](../02-architecture.md), ADR-0004.
- **Context**: HKT's workshop asks for a signed AgentDelegationCredential with merchant and category allowlists, a spending limit, expiry and a confirmation threshold, and names W3C VC 2.0, OpenID4VC and DIDs [F19]. Our first mandate was a plain signed JSON object.
- **Decision**: The mandate is a W3C VC Data Model 2.0 credential of type AgentDelegationCredential: issuer = delegator did:key; `credentialSubject.id` = agent did:key, plus intent text and rules (budget, per-purchase cap and `ask_above`, categories and merchants, seller check, velocity); `validFrom`, `validUntil`. Proof: Data Integrity, cryptosuite `eddsa-jcs-2022`, carrying the document's `@context`. The engine reads a domain `Mandate` from `mandateFromCredential`; R1 verifies the proof against the pinned delegator did:key; `MANDATE_SEALED` carries the credential.
- **Consequences**: A judge can read a standard credential and check it offline; golden vectors and the W3C vc-di-eddsa test vectors pin our proof code. A top-up is a new credential, never an edit. Cost: JCS and multibase must be exact, so they are tested on published vectors.
- **Rejected alternative**: A JWT envelope (VC-JOSE) or SD-JWT. Widely supported, but selective disclosure buys nothing for one delegator, and JCS keeps one canonical form for the credential and the log.
