# apps/web

- **What**: the booth UI (Vite + React 19), mobile first, EN with a zh-HK second line. The rail is SIMULATED on every screen.
- **Three clients, one interface** (`ApiClient`, `src/api/types.ts`): `HttpApiClient` (`src/api/http/`, live mode) when the booth server answers `/api/info`, else `LocalApiClient` (`src/api/local/`, on-device mode: the real engine, log and SIMULATED rail in the page, recorded planner and judge answers, no network, a note on screen). `?api=local` or `VITE_API=local` forces on-device mode; `?api=mock` is for tests. `MockApiClient` is a UI-test double only. All pass `test/apiClientContract.ts`.
- **What the booth can do** (`info().features`): `ask` shows the typed field in the Ask sheet (where no live planner runs, the fixed keyword reader finds the items instead, see Show Wally a photo), `alternatives` shows "See cheaper options" after a budget stop (after the Demo button "Shipping tips it over" the replan runs over the three demo clothes named in `data/scenarios/booth.json`, `overflow.cheaper`), `compile` says who reads the Seal sentence (`model` or the fixed `rules`). `see` (`model` or `palette`) says whether the booth's model reads pictures in Show Wally a photo (below). `exportLog()` (live and on-device) adds Receipts > Export for the offline verifier.
- **Portable backend** (`src/booth/backend/`): the booth runner, session and `OrchestratorBackend`, no `node:` import; the server and `LocalApiClient` both run it. Key design for the phone: `src/api/local/KEYS.md`.
- **Booth server** (`server/`, Hono, 127.0.0.1 only unless LAN mode): `pnpm demo` from the repo root (preflight, build if needed, start), then open the printed URL. `pnpm demo:reset` resets keys, logs and the packet. `pnpm demo:lan` is the same server for phones on the Wi-Fi (section below).
- **Stop texts**: `src/explain/renderStop.ts` wraps a stub; lane A's `render` replaces it in one line.
- **On-device session kept** (`src/api/local/persist/`): a reload no longer starts a new budget. The log and the two throwaway demo keys are stored under `wally:session:v1`, verified on boot (keys, hash chain, head, budget not ended), and the SIMULATED rail is rebuilt from the log; any failure starts fresh with one calm line in the on-device note. Start the demo over deletes it; a family budget is not kept; several tabs: last writer wins; on GitHub Pages the storage is shared by every project site of the owner. `PersistentLocalApiClient.open()` is what `pickClient` opens; `new LocalApiClient()` still keeps nothing. Details and limits: `src/api/local/KEYS.md`.

## Phones on the booth Wi-Fi
- **Start**: `pnpm demo:lan` from the repo root: preflight with the LAN checklist (`node scripts/booth-check.mjs --lan` alone prints just that), build if needed, server on `0.0.0.0:8787`, LAN mode ON. `PORT` works; `HOST` names another bind and any non-loopback `HOST` also turns LAN mode on. Without `--lan` or `HOST` nothing changes: 127.0.0.1 only, no token.
- **Show the code**: open `http://127.0.0.1:8787/#/booth` on the Mac. About (the info button) and Presenter show "Open Wally on your phone": a QR code, the links, Copy link and a "LAN mode is ON" chip. Nothing shows on any other page, or when LAN mode is off (`/api/lan` is a 404 there).
- **Phone**: scan with the camera and tap the link. `/?t=<token>` sets a cookie (`wally_t`, HttpOnly, SameSite=Strict) and redirects to `/` without the token. The phone must be on the same Wi-Fi as the Mac. The `.local` link works on iPhones; some Android phones need the IP link.
- **Token**: 128 random bits, new on every server start, so a restart means scanning again. Every `/api/*` call needs it (header `X-Wally-Token` or the cookie) except `/api/health`; the app files need none. The Mac's own pages need none (loopback Host and peer). Wrong or missing: 401 JSON. No other hardening: plain http, one shared token.
- **Host and Origin**: Host must be loopback, one of the Mac's non-internal IPv4 addresses, its hostname or `<hostname>.local`, any port. A POST Origin must be the page's own address, a loopback page, or a native shell (`capacitor://localhost`, `http://localhost`, `https://localhost`). Those three get CORS: the origin is echoed (never `*`), headers `content-type, x-wally-token`, `X-Event-Seq` exposed.
- **macOS firewall**: the first start may ask to let `node` accept incoming connections. Click Allow, once, on the Mac. If a phone times out, check System Settings, Network, Firewall.
- **Wi-Fi client isolation**: venue and hotel Wi-Fi often stops phones from reaching other devices. The page never loads, or `/api/health` times out from the phone. Use the Mac's own network (System Settings, General, Sharing, Internet Sharing) or a phone hotspot that the Mac joins.
- **Add to Home Screen** (iOS): works over http as a web clip with an icon and full-screen launch. Plain http is not a secure context: no service worker, no install prompt, no offline mode. The clip may start without the pairing cookie and then shows on-device mode: open the QR link in Safari instead.
- **Native app**: About, "Connect to the booth Mac". Paste the link (Copy link on the Mac, then Universal Clipboard on an iPhone). Only a 192.168, 10, 172.16 address, loopback or a `.local` name is accepted. The Mac is asked for `/api/info` with the token first; only an answer saves the address (`wally:server`, `wally:token`) and reloads into live mode. The first call on an iPhone shows the local network permission prompt: Allow, then Connect again. "Disconnect" goes back to on-device mode. Native config: `apps/mobile/README.md`.
- **Browser storage keys**: `wally:token` (session storage; local storage in the native app), `wally:server` (local storage, native app only), `wally:session:v1` (local storage, on-device mode: the kept session; the key carries the version), `wally:wallet` (a practice-wallet id, only for a client that gets it in a header; beside the token). A page address with `?t=` (a dev server in front of the booth server) is read once and cleaned.

## Practice wallets (every phone its own budget)
- **Why**: the booth was one shared wallet, so five phones tapping Buy a cotton tee drained the HK$800, hit R7 (3 cards per 10 minutes) for everyone, left five open Needs your OK questions, and one judge's Try to tamper changed the next judge's Proof. Now a phone that scans the QR gets a wallet of its own; the Mac stays the one operator-driven wallet.
- **Who gets what** (`server/sessions.ts`, `server/sessionScope.ts`): a request from the Mac (Host and socket peer both loopback) always gets the shared booth wallet, as before, no cookie. Any other client that passed the pairing token gets the wallet named by cookie `wally_s` (HttpOnly, SameSite=Strict, Path=/, 128 random bits, set once, on its first `/api/*` answer) or by header `X-Wally-Session`. A native shell or script that keeps no cookie sends the header (`new` or its id) or comes from a shell origin, reads its id from the same header of the answer, and sends it back; `HttpApiClient` does this. The header wins over the cookie. An id the server does not know, or one that ran out, gets a fresh wallet under a new id (never an error, never an id the client chose).
- **A wallet is a second booth**: its own throwaway demo keys, in-memory log (nothing in `LOG_DIR`), orchestrator and event stream, the ready-made budget sealed at once. Laya and Qwen are shared. Reset, Cancel this budget, Try to tamper, Needs your OK and the exported log files (they verify with that wallet's own keys) are all per wallet. `/api/health`, `/api/lan` and the app files are global.
- **Limits**: 12 visitor wallets. A wallet with a page open, or used in the last 5 s, is never dropped to make room (its page would reconnect at once with the old id, get a new wallet and drop the next one: 13 pages at a cap of 12 made 20 drops in 5 s in a simulation); of the others the one used longest ago goes. When none can go the next visitor gets a plain 503 "every practice wallet is in use" (the app then runs on the device) and no work is done for them. A wallet is dropped after 45 idle minutes; a page with its event stream open counts as in use and restarts the idle time, so a phone that locks after an hour of reading keeps its wallet. One timer for all of them, cleared on close. It beats every 5 s and ticks only the wallets that have a page open: a tick reads the whole log (about 0.8 ms per entry), and 12 wallets of 40 entries ticked every second took 60% of a core on an idle Mac (now about 0.3% with no page open and about 3% with 12 pages open) [F113]. Every request ticks its own wallet first, so a slower beat only delays the expiry events pushed to an open page. Making a wallet takes 8 to 12 ms (MEASURED, n=36, see Crowd check below; the limit was 300 ms) [F111].
- **Turns at the models** (`server/gate.ts`): the visitors' runs that reach Laya or Qwen (scenarios, propose, ask, cheaper options, escalation answers, the sentence reader) take turns, 2 at a time, in the order they came, one place per wallet; 48 may wait, a longer line gets a plain 503 "Wally is busy". The Mac's own wallet does not wait in that line. Without it, 12 phones tapping in the same second queued inside Laya and the last decisions ran past the 1.5 s judge deadline [F34] and escalated (7 of 12 phones saw Needs your OK in the first round).
- **Bounds against a loop** (any holder of the shared pairing token [F92] can script one): a visitor wallet takes no more runs after 200 log entries (409 `WALLET_FULL` "start the demo over from About"; reads, Verify and Reset still work), because every request reads the whole log (607 entries made one request take a second); a HEAD from a visitor is 405 (it would run the event route and leave a client nobody closes, which guards a wallet from being dropped); `/api/health` and `/api/lan` skip the token for GET, so they never make a wallet whatever the method; a header that is not an id is ignored for who the wallet is. Not bounded: a holder can still fill the 12 places (every phone has the token by design); restarting the booth server rotates the token and drops every wallet.
- **Switch**: `WALLY_SESSIONS=on|off`, default on when LAN mode is on, off otherwise; a value that is neither fails closed to off with a line at start. Off changes nothing anywhere (one shared wallet, no cookie, `/api/info` has no `sessions`). `/api/info` says `sessions: "shared"` to the Mac and `"private"` to a phone; About shows one calm line on a phone that has its own.
- **Practice-copy link**: `WALLY_PUBLIC_URL` (http or https) adds a second QR code and link under the Wi-Fi one on the Mac, "Works anywhere (practice copy, sample shop)": the on-device app, for a phone that is not on this Wi-Fi. Unset or odd: not shown.
- **Known limits**: a browser that blocks cookies gets a new wallet on every call and fills the places until they are all in use (the wallets it leaves behind have no page open, so the next visitor can drop them); the Mac's own LAN address opens a visitor wallet, only 127.0.0.1 and localhost are the booth; wallets and ids live in memory and go with a restart or a drop, and a page that held one is given a fresh wallet when it asks again (never an error) and reads it when its stream comes back (`test/http/reconnect.sessions.test.ts`); a page left asleep for more than 45 minutes with no stream finds a fresh HK$800 budget; a 13th phone while 12 pages are open is turned away; plain http, one shared pairing token.
- **Tests**: `test/server/sessions*.test.ts` (registry, isolation matrix with two cookies, loopback, header, cookie flags, cap, idle drop, SSE, close, CORS), `test/server/gate.test.ts`, `test/http/httpContract.sessions.test.ts` (the client contract as a native shell), `test/sessionsClient.test.ts`, `test/sessionsUi.test.tsx`, `test/server/publicUrl.test.ts`.
- **Crowd check** (`scripts/sessions-crowd.mjs`): with `pnpm demo:lan` running, `node scripts/sessions-crowd.mjs --port 8787 --phones 5 --seconds 120` plays that many phones at once through the Mac's Wi-Fi address (token and address come from `/api/lan` on the Mac). It checks that no run id reaches two phones' streams, each phone buys three tees and has its fourth stopped whatever the others do (budget and R7 per wallet), no budget goes negative, every card equals its approved cart (I2), every exported log passes `pnpm verify-log`, and the Mac's own wallet did not move. Exit 1 on any failure; files go to `--out`. `scripts/sessions-crowd-ui.mjs` is the same with real pages: Playwright's phone-sized Chromium contexts open the QR link and tap through the app (needs the built UI), then check cookies, four taps together, that each page's meter equals its own wallet, and that the Mac's wallet did not move. 2026-10-03, Laya and the rule planner on the shared dev Mac: 5 phones, 120 s, 883 calls, 7,871 stream events, 0 error answers, all PASS; scenario calls p50 696 ms and p95 1,092 ms client-timed (they include the turn at the judge); judge status OK on 56 of 56 decisions in the final logs, p50 296 ms, p95 400 ms, max 434 ms [F112]; a wallet is made in 8 to 12 ms (n=36) [F111]. 12 phones, 60 s, same checks: PASS with judge status OK on 94 of 94 (p50 242 ms, p95 381 ms, max 680 ms); without the turns at the models the same run gave 2 judge TIMEOUTs in 105 decisions and 7 phones with Needs your OK in the first round (p50 984 ms, p95 1,352 ms, max 1,501 ms).

## Live link (GitHub Pages)
- **What**: the on-device app as a static site, so a judge opens `https://<owner>.github.io/<repo>/` and uses the real engine, signed log and SIMULATED rail in the browser. Recorded planner and judge answers, no booth server, no key. The first load needs the network; after that the service worker opens it offline. The offline verifier sits at `verifier/` under it. Keys and limits are those of on-device mode (`src/api/local/KEYS.md`).
- **Build**: `pnpm pages:build` from the repo root writes `apps/web/dist-pages/` (gitignored): the verifier page built first (into a temp folder), then the web build with `VITE_API=local` that carries it as `verifier/index.html` (`WALLY_VERIFIER_FILE`, so the service worker precaches it), an empty `.nojekyll`. The script ends with the layout, size and precache checks. `apps/web/dist` (the booth build) is never touched.
- **Test**: `pnpm --filter @wally/web e2e:pages` builds, then serves `dist-pages` under `/wally/` on 127.0.0.1:8801 (nothing at the origin root, as on a project site) and checks in Chromium: boots on-device with no `/api` request, worker scope and cache under `/wally/`, manifest and icons inside it, a Try asking purchase shows the one-off card, every screen's chunk loads, Proof opens `/wally/verifier/` and it verifies its demo log, and with the server gone a reload still shows the app, a purchase still runs, and Open the offline checker opens from the service worker (all three addresses of it) and verifies its demo log. Not in the default `e2e` list. Unit tests: `test/pagesRules.test.ts`, `test/pages-build.test.ts` (a real build into a temp folder), `test/pagesServer.test.ts` (the Pages-like server).
- **Why it works from a sub-path**: relative URLs and hash routes. `vite.pages.config.ts` adds `build/pagesPlugin.ts`: the Proof screen's `/verifier/` link is made relative, the manifest `id` is dropped (`./` is read against the origin, so it would name the origin root, shared by every project site on that github.io), and any root-absolute URL left in the written html, script, style or manifest fails the build. When `VERIFIER_HREF` in `screens/proof/components/ProofSheets.tsx` is built from `import.meta.env.BASE_URL`, the link rewrite can go.
- **Publish** (owner, once, after the repository is public): 1. Settings, Pages, Source: **GitHub Actions**. 2. Actions, **pages**, Run workflow (or push to main). 3. Open the URL in the run's deploy job (`https://<owner>.github.io/<repo>/`).
- **Workflow** `.github/workflows/pages.yml`: runs on push to main and by hand; the job is skipped while the repository is private, so it stays green. Needs `pages: write` and `id-token: write`, set in the file.

## Design decisions (polish lane A)
- **Variant pickers (dev server only)**: `WALLY_API_PORT=<your booth port> pnpm --filter @wally/web dev`, then open `http://127.0.0.1:5173/?api=local#/styleguide/variants/home` (or `/seal`). Keys `1`-`3` or arrows flip, `R` replays, `?v=2` keeps the choice, `?chrome=0` hides the scene strip. `import.meta.env.DEV` guards the import, so the pickers and the losing variants are not in `dist/` or the PWA precache (checked: no `proto-picker` and no variants chunk in a production build). The dev server boots again: `vite.config.ts` stubs `node:fs` and `node:path` for the browser graph in dev only, and `WALLY_API_PORT` points its `/api` proxy at your own booth server instead of 8787.
- **Budget hero** (`/variants/home`): Greeting shipped, over Ring and Action first.
  - **Greeting**: Wally and a speech bubble above the card; the bubble says what the budget is doing (ready, shopping inside the rules, needs your OK, all used, cancelled, ended) and Wally's face follows. Won because the gap was character and status, not data, and the card's contract (chip, meter, tags, headings) stays as it was.
  - **Ring**: one ring for left, held and spent on a light card. Best in dark and at reading spent against held; lost because a fresh budget is a full empty-looking circle, it drops the brand gradient, and the legend wraps in 繁 and at 360 px.
  - **Action first**: compact card and one-tap tries in the first screen. Best for starting the demo; lost because it repeats Try asking, clips the rule tags and moves the Try asking cards the tests count.
- **Seal moment** (`/variants/seal`): Lock shipped, over Hold and Signature.
  - **Lock**: the padlock closes where you pressed, the haptic fires on the same frame, the card is stamped Signed and the button reads Sealed in green; then the sealed screen takes over (`--dur-ceremony`, 0 under reduced motion).
  - **Hold**: press and hold the lock, the shackle follows the finger. Kept as a prototype; it changes how the key action is done and a judge may not find it.
  - **Signature**: a signature draws across the card. Charming; it loses the padlock, which is the product's picture of "sealed".
- **Libraries**: NumberFlow adopted for the budget amount only (+8.1 kB gzip initial JS in all, 234.1 to 242.2 kB, with the hero and the rest of this lane; plain text where it cannot run, so tests and old browsers see the same figure). Rejected: **motion** (CSS transitions, `@starting-style` and CSS `linear()` springs cover every motion here and a library would cost 15-30 kB), **base-ui** (the Sheet, Dialog, Segmented and Switch primitives already trap focus, rove and name themselves, and are covered by the UI component tests; swapping them is a rewrite), **Sonner** (one toast at a time, rare; the existing one is 88 lines).
- **Motion tokens added**: `--dur-exit` (leaving is quicker), `--dur-settle`, `--dur-roll`, `--dur-stagger`, `--dur-ceremony`, and the easings `--ease-drawer`, `--ease-settle` and `--ease-pop` (the last two are real springs where CSS `linear()` exists). All are zero under reduced motion; `src/design/motion.ts` mirrors the ones JS needs, with a test.
- **Rules kept**: no `backdrop-filter` (the branding guard bans glass; the sticky Seal bar gets a fade instead), no raw colours or raw durations in component CSS, hover styles only under `(hover: hover) and (pointer: fine)`, and nothing animates on the first paint of a data list.

## Design decisions (polish lane B: action and proof)
| Route (dev server only) | Compares |
|---|---|
| `#/styleguide/variants/run` | index of the three moments |
| `#/styleguide/variants/run/stopped?v=1&c=budget` | Stopped before paying: Quiet guard (shipped), Ghost card, Where it stopped. Cases `budget`, `seller`, `injected`, `off` |
| `#/styleguide/variants/run/card?v=1&c=ready` | The one-off card: Wallet card (shipped), Ticket stub, Live card. Cases `ready`, `declined`, `paid`, `replay`, `drift` |
| `#/styleguide/variants/run/ok?v=1` | Needs your OK: Consent sheet (shipped), Hold to approve, Permission slip |

- **Picker**: keys `1` to `3` and the arrows flip, `R` replays the entrance. The page is the real shell around a real result from the mock client; nothing in `StyleGuideRoute.tsx` loads it in a production build (`import.meta.env.DEV`), so it is not in the bundle or the PWA precache. Run it with `pnpm --filter @wally/web dev` (`WALLY_API_PORT=<port>` points the /api proxy at another booth server; a dev-only plugin in `vite.config.ts` stubs the `node:` modules the on-device bundle reaches, so `?api=local` and `?api=mock` work there too).
- **Stopped before paying**: one calm card, the reason first, the four-step path (picked, read, rules, no card), a green strip that says no card was made and the budget is untouched. The pink slab, the ghost card (duplicates the strip, a stamp reads as shouting) and the settled steps list (buttons fall below the fold, the reason hides in a step) lost.
- **The one-off card**: the card is the hero, the amount big, a live "ends in" clock and life line, Pay now directly under it, a stamp when used, cancelled or expired. The ticket stub (taller, reads as a coupon) and the live ring card (the time twice) lost. One `OneOffCard` (`screens/console/`) serves Wally and Budget.
- **Needs your OK**: a consent sheet that spells out what yes does, the clock, both answers pinned, and "signed and saved as a receipt". Hold to approve adds friction to every demo; the slip is calm but a long in-page block.
- **Libraries**: none added to the app. NumberFlow is not used on these screens: the one figure that moves in front of the person here is Budget left (a short count-up hook with a plain-text start), the card amount never changes, and its custom element hides digits from `getByText` and the Playwright checks (lane A uses it for the Budget hero). motion is not used (CSS, WAAPI and the existing sheet drag cover every gesture), nor base-ui or Sonner (the Sheet, Dialog and Toast primitives exist and meet the focus and dismissal rules). The only new dependency is the axe scanner for tests.
- **Voice in the Ask sheet**: a mic inside the field, shown only where the browser has a speech recogniser and not in the Capacitor shells. It uses the browser's own speech service, so audio may leave the device: the first press only says so, and nothing is sent until the person presses Send. A gap to say out loud: voice does not work offline, so it is not part of the local-first claim.
- **Offline verifier** (`apps/verifier`, still one file with no network): the app's look and icons, one language at a time with an EN|繁 toggle (both texts stay in the page, CSS shows one), dark mode, a verdict card and entry rows that light in once from CSS. On a phone the buttons, verdict and entries come before the three text areas. `pnpm --filter @wally/verifier e2e` opens the built file from `file://` offline. The Proof link to `/verifier/` works under the PWA because `swPolicy.classify` leaves that path to the network (it used to get the app shell back).
- **Not in this pass**: Pills layout in the Ask sheet and the Sheet's focus ring on the close button belong to lane A's primitives (the ring shows only when a script opens a sheet with no pointer touch before it). Mock and server error messages that still say mandate (`Connection.tsx` shows them verbatim) and the engine's "Details for nerds" sentences live outside the UI code.

## Display modes (plain-dev lane)
- **Two views, one switch**: `plain` is the default for everyone on every host (booth, phone, on-device, native); `developer` is today's screens with hashes, rule ids, intervals and raw codes. About > "Show technical details" flips it and the choice is kept in `localStorage["wally:mode"]` (every access guarded; blocked storage still holds for the page). `?dev=1` forces developer and `?dev=0` plain for one page load without storing anything (a demo link); flipping the switch takes `dev` out of the address so the two never disagree. The offline verifier page reads the same key and the same parameter.
- **Store**: `src/state/displayMode.ts`, a module store read with `useSyncExternalStore`, no provider: `useDisplayMode()`, `useIsDeveloper()`, `readDisplayMode()`. Tests open a screen in developer mode with `test/helpers/devMode.ts` (`developerMode()` sets `?dev=1`; the address goes back after every test).
- **Evidence in plain words** (`#/evidence`, and Presenter DM8): `src/evidence/plainModel.ts` reads one loaded run into the counts the cards show for each layer (rules only, Wally = rules plus the listing check, an AI on its own for reference). `explainPlain.ts` and `explainCards.ts` are the glossary: fixed templates in EN and zh-HK, no model prose, unit-tested; a sentence never says more than its counts (every only for n of n, none only for 0 of n). `components/plain/` draws the cards. Rules that hold there: a zero is always followed by the limit it could still hide (the top of the 95 percent Wilson interval for 0 of n, computed from n, shown as parts of a hundred); the chip is shown once per card in plain words ("Measured on 150 of our own test shoppers, in a simulated shop") and opens what it means; rules only and Wally lead every comparison and the AI on its own is the last, quietest row; the false alarms (5 of 66) are on the Approved card as well as in the miss card; no count of tests or files is printed. "How we know" mounts the developer view in place.
- **Proof and Receipts in plain words**: `src/screens/proof/` (`PlainProof`, `PlainStatusCard`, `PlainTimeline`, `PlainDemo`, `useProofCheck`). The screen checks the receipts itself when it opens (once per log state, never in a loop) and leads with a verdict; the timeline numbers receipts from 1 and says each one in words; "Show the details" per receipt holds the fingerprint and the failed check's code; the raw JSON and the entry kind are developer only. No internal entry kind (MANDATE_SEALED, DECISION, CARD_EVENT) is printed outside developer mode, closed disclosures included (`test/plainApp.test.tsx`, `test/plainProofKinds.test.tsx`).
- **A changed copy is never quiet**: while the tamper demo is up the booth shares the changed copy with the next visitor, so Proof and Receipts open with a `role="alert"` banner ("You are looking at a changed copy of the receipts") that holds a one-tap Restore, in both modes; the changed rows are tagged. Every client's view carries the copy in `entries` and says what it changed in `tampered`, so `state/storedEntries.ts` puts the original number back to rebuild the stored log; Budget, Wally and the Presenter read the stored log, Proof and Receipts read the copy.
- **Presenter and the checker page**: DM3 to DM5 give each stop's plain reason (the same sentence the Wally screen gives, figures chipped; developer mode keeps the engine's "Stopped by R3" sentence), DM7 reads like Proof, DM8 is the plain Evidence stage, and DM9 is the same three columns and claims in words (`evidence/dm9Plain.ts`, line for line with `dm9.ts`, held by a test). The offline checker (`apps/verifier`) has its own switch on the same `wally:mode` key, so on the Pages origin the app's switch reaches it.

## First run, a profile, and a shopper's Home (lane onboarding)
| Key (localStorage) | Holds |
|---|---|
| `wally:onboarded` | `1` once the first run was finished or skipped; with it set (or with `?booth=1` in the address) the first run never shows. A setup step that throws, or a booth that never answered, does not set it, so the first run comes back |
| `wally:profile:v1` | the profile: nickname, style, colours, sizes, what the person shops for. Versioned key and `v`; strict read (unknown ids, other versions and corrupt text are dropped); never sent anywhere |
| `wally:demo-open` | `1` or `0`: the person's own choice for the Demo scenarios disclosure on Home |
| `wally:presenter` | read only: `1` opens the Demo scenarios (presenter mode; one line in `screens/home/demoMode.ts` follows the display-mode switch) |

- **First run** (`src/screens/onboarding/`): shown once per browser, only when the app opens on Budget (a link to any other screen is left alone). Four steps: Hello (language, nickname), Your taste (style, colours, sizes, what you shop for), Your first budget (presets, how long, whose money when the booth offers family, verified sellers, then the Seal screen's own Check and seal moment), and a quick tour of three coach marks on the real Budget screen. **Skip** is on every step; Skip then Skip tour is two taps to the live demo. Skip keeps what was typed on Hello and Your taste. A Skip that cannot seal the ready-made budget stays on the step and says why (the next press tries again); a step that throws, or a booth that never answered, lets the visitor into the app with the ready-made budget sealed and the first run not counted as seen. Try again after a failed load comes back to the same step. The tour is modal (the page behind is inert, a tap on the dim layer keeps focus on the card, Escape ends it wherever focus is) and runs only on Budget. The setup steps are a lazy chunk (4.8 kB gzip, with 4.3 kB of Seal code it shares and 2.5 kB of CSS) and the tour another (2.0 kB), so a returning visitor loads none of it. Initial JS grew 9.7 kB gzip (253.6 to 263.5 kB) for the store, the strings, the gate and the new Home.
- **The ready-made budget**: `BoothProvider` seals the HK$800 budget [F20] itself when nothing is sealed. The first run passes `autoSeal={false}` while the visitor sets up their own; when it turns on later the booth is read again and the budget is sealed only if there is still none (once per connection). A booth that already holds a live budget (the live server seals one when it starts) skips the form: "Your budget is ready". A budget that is cancelled, ended or used up gets the form, and Check and seal says that sealing starts a new budget and new receipts. `#/seal?mode=welcome` still shows Meet Wally.
- **Switching it off**: set `wally:onboarded=1` before the page opens. `test/setup.ts` sets it before each test and puts it back after any `localStorage.clear()`; `playwright.config.ts` and the Pages spec put it in `storageState`; `e2e/onboarding.spec.ts` clears it. A test of the first run removes it after the clear (`test/helpers/firstRun.tsx`).
- **The profile is a hint, never a rule**: it changes the greeting, the order of the scenario cards and a "For you" tag (`screens/home/tryRank.ts`), the four Ideas for you (`screens/home/ideas.ts`), the Ask example, and what the Seal screen starts from. It never reaches the engine, the planner or the judge; what the person shops for only starts the first budget's form (categories and amount), which they review and sign. Every item it names is on the shelf (`test/ideas.test.ts` reads `data/fixtures/listings`). Colours and sizes are kept and shown back, not used to rank: the shelf has no variants. About has "Take the tour again" and "Forget my profile" (removes the profile only; if the browser refuses the removal it says the profile is only hidden). "Start the demo over" also clears the profile on the device, and its dialog says so when there is one, so a shared device does not greet the next judge by name.
- **Home** (`screens/home/`): Wally's greeting, the "What do you need?" row (one control; opens the Ask sheet, camera and microphone drawn on it; `PhotoCardSlot` in `slots.tsx` is where the photo lane's card goes), the budget card, Ideas for you (a tap opens a preview sheet; its **Ask Wally to buy this** asks Wally for the item as if typed, or runs its booth scenario on a booth that cannot take a typed ask), Recent, **Demo scenarios** ("(for judges)" on the booth Mac only; the booth's scenario cards in a disclosure) and, last, Manage this budget (the "Cancel the budget" card scrolls to it, and from the cards above it that is a short way). Closed for a shopper; open on a loopback address (the booth Mac, not the native app), with `?booth=1` and in presenter mode; the person's own choice is remembered.

## UX pass (lane ux-pass)
- **Home order** (`screens/home/BudgetScreen.tsx`, `BudgetHero.tsx`): the greeting, then What do you need? (and the photo card) above the figures, then the compact budget card. A waiting "Needs your OK" comes first. Add to Home Screen (`pwa/InstallUi.tsx`) shows only after a first completed purchase or on a second visit (`pwa/visits.ts`), below Recent.
- **Idea preview** (`IdeaPreviewSheet.tsx`, `ideaListings.ts`): an idea card opens a sheet first: a drawing, the item, the shop, the price in HK$ with SIMULATED, "From the demo shop", **Ask Wally to buy this** and **Not now**. Only the first button asks Wally. The price is the fixture listing's price plus shipping (none is typed in a string). The drawing is `IdeaArt.tsx`, a plain placeholder by kind, with one place to swap in the photo shop's art. The booth's scenario cards still run at once.
- **Receipts, one purchase one row** (`screens/proof/purchases.ts`, `PurchaseRow.tsx`): the decision, its one-off card and its charge (the `resolves` chain) are one row with a "3 steps" expander, worded by where the purchase ended (paid, stopped, needs your OK, cancelled, card expired). One receipt number everywhere in plain mode (`receiptNumber(seq)` = log number + 1: Home Recent, Receipts, Proof, Wally's result, the steps); a purchase row carries the number of the receipt it opens (the charge for a paid purchase), so the row, its sheet and Proof agree. Developer mode keeps the flat list and `#seq`.
- **Dead ends** (`screens/run/`): a stop on the categories names the budget's own ("Your budget is for Clothes only") and offers **Edit rules** (a new budget; the note says so). After a cancelled or ended budget every stop and the Ask lead to **Start a new budget**. "See cheaper options" with nothing found says what was tried and offers **Change the amount** or **Pick something else**. The OK countdown says "Wally waits 60 seconds, then cancels this for you" (the number is the question's own window). A question still open when its budget ends is `CLOSED` in the view (`packages/core` `log-view.ts`; no decision or log entry changes): its sheet says so and has no Approve. An answer that lost a race reads "Already answered on another screen".
- **Words**: the SIMULATED chip in the top bar is a button that says "The shop and the card are a safe practice version. No real money moves." (Developer mode keeps the rail sentence); the first-run and Seal flow say **Lock in** where they said Seal; About lists Presenter mode and Style guide only in Developer mode or on the booth host; Why trust Wally opens on a headline and a short list with the rest under disclosures; the on-device note reads "Demo mode: Wally runs here on your phone with sample shop data. Nothing leaves your phone." (`api/local/info.ts`).
- **First run**: while no budget exists a note under the Skip link says what Skip does ("Skip uses a ready-made HK$800 budget for clothes", the amount read from the booth's own sentence, SIMULATED). The top bar is after the step in the page and first on screen (CSS `order`), so Tab goes through the step, then Skip, then Back and Next. A typed amount above one card's limit [F1] is cut to it with a note, as a date is cut to the longest a budget may run; money text too large to hold is not an amount (`dollarsToMinor` returns null) and the Seal screen says "That amount is too large."
- **Seal examples**: every example sentence the Seal screen ships, in English and 繁體, reads back into the same budget and rules through the fixed reader (`test/sealExamples.test.ts`); `booth/zhReader.ts` adds 八百蚊, 800蚊, 港幣, 衫 and 鞋 and 雜貨, 兩星期內, 十月尾 and 超過HK$300要問我.
- **Reconnect** (`api/http/eventStream.ts`, `hooks/useBooth.tsx`): when the live stream comes back after a break, the phone wakes, or the network returns, the page reads the booth again and shows it as it is (`resync` in the reducer keeps the finished runs of the same log and drops the rest) and clears a "could not be reached" message; a message that is a refusal stays. The mock and on-device clients have no connection and none of this runs there.
- **Layout under stress**: the top bar wraps at large text (a container query in `em`, so it follows the text size), a 24-letter nickname wraps in the greeting and in About, list subtitles wrap long words (`design/ui/surface.css`). Not done: the bottom tab bar at 200% text.
